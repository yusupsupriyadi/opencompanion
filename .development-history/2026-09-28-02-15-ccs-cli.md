# CCS CLI support

## Summary

Added CCS (`@kaitranntt/ccs` 8.10) as a fifth CLI. CCS starts Claude Code as `ccs [profile] [claude args]`, so it reuses Claude Code's flags, stream-json parsing, hooks, waiting detection, model catalog and transcripts. The CCS extra arguments from Settings go right after `ccs`, so the profile comes first.

## Changes

- `src-tauri/src/ccs.rs`: profile from the extra arguments, default/account ("plain") profile check via `~/.ccs/instances/<name>`, Claude config folders CCS uses.
- `src-tauri/src/cli.rs`: `CliKind::Ccs`, `runs_claude_code()`, tested line 8.10.
- `src-tauri/src/headless.rs`: `split_extra` puts CCS extra arguments first; Claude flags for CCS.
- `session.rs`, `orchestrator.rs`: profile arguments lead; hooks only for plain profiles; headless and Chat planner refused for API/CLIProxy profiles.
- `events.rs`, `waiting.rs`, `models.rs`, `transcript.rs`, `monitor.rs`: CCS handled like Claude Code; transcripts and model catalogs also from `~/.ccs/instances/*`; outside scan lists the CCS process, not its Claude child.
- Frontend: `CliKind` type, label, "CCS" text mark, install command, CCS-specific extra-args help, en/id strings, fixture and a Settings test.
- `README.md`, `CHANGELOG.md`: CCS column and limits.

## Decisions

- Checked CCS 8.10 source: API/CLIProxy profiles pass their own `--settings` (a second `--settings` replaces the first, verified with Claude Code 2.1.283), and API profiles route `-p` through CCS delegation, which reads the next argument as the prompt. So those profiles get interactive sessions without hooks only.
- No CCS logo was created (asset rule); the mark is the text "CCS", like "OC" for OpenCode.

## Verification

- `ccs claude-1 --version` forwards to Claude Code (`2.1.283`); piped stdout gets no CCS update notice.

- No full session through CCS was run from the app (no smoke test without approval).

- `CCS_DIR`/`CCS_HOME` overrides are not read; `~/.ccs` is assumed. Skills screen has no CCS column.
